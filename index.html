Case Study 01  ·  Predictive Modelling, Pipeline Auditing & SHAP Explainability  ·  Completed Portfolio Project

Diabetes Risk Screening — Predictive Modelling & Pipeline Audit on 10,000 Synthetic Patient Records

An end-to-end data analysis, pipeline debugging, and explainable classification case study built on a synthetic 10,000-patient Type 2 diabetes dataset, delivered with a five-page Streamlit decision-support application. This project is an educational and portfolio screening study on synthetic data, not a clinically validated diagnostic tool or medical device.

1. Project overview & problem context

Predictive screening models in healthcare frequently appear to achieve near-perfect accuracy in notebooks while concealing silent data-pipeline defects, post-diagnosis target leakage, or train/serve feature mismatches. This project investigates a 10,000-row synthetic African Type 2 diabetes dataset (diabetes_t2dm_africa_extra_large_10000.csv), audits and repairs five pipeline defects in the baseline workflow, compares six classifiers, and provides feature-level SHAP explanations in a Streamlit interface.

2. Objectives & technology stack

  • Eliminate post-diagnosis complication columns and audit preprocessing so all 22 pre-diagnosis clinical inputs and 4 engineered ratios reach the fitted model.
  • Compare six classifiers under 5-fold stratified cross-validation with in-fold SMOTE and evaluate SHAP explainability speed and fidelity.
  • Stack: Python, pandas, NumPy, scikit-learn, imbalanced-learn (SMOTE), XGBoost, LightGBM, CatBoost, Optuna, SHAP, Matplotlib, Seaborn, Streamlit.

3. Dataset structure, missingness & diagnostic label constraints

The source dataset contains 10,000 synthetic patient rows with demographic attributes, pregnancy history, boolean clinical risk factors, laboratory measurements, and 16 post-diagnosis outcome or complication columns (such as diagnosed, years_since_diagnosis, on_medication, retinopathy, nephropathy, and diabetic_foot_ulcer). In this dataset, 74.6% of records are labeled diabetic (the majority class), while Normal and Prediabetes rows form the 25.4% minority class.

  • Removing post-diagnosis leakage: All 16 post-diagnosis and complication fields plus patient_id are dropped immediately on load so the model only sees pre-diagnosis screening variables.
  • Biologically implausible zeros vs. structural nulls: Zero values recorded in seven laboratory fields (fasting_glucose_mg_dl, hba1c_percent, total_cholesterol_mg_dl, ldl_mg_dl, hdl_mg_dl, triglycerides_mg_dl, creatinine_mg_dl) are converted to NaN for median imputation inside the pipeline. By contrast, parity is recorded only for the 1.4% of patients who are currently pregnant; its 98.6% null rate is structural, so non-applicable rows are explicitly set to 0 rather than imputed from the pregnant subgroup median.
  • Critical label-construction finding: A single threshold check on the two diagnostic blood tests included among the features—fasting_glucose_mg_dl ≥ 126 OR hba1c_percent ≥ 6.5 (the standard WHO/ADA diagnostic cutoffs)—matches the dataset's target label 99.24% of the time.

4. Technical implementation & five pipeline bugs resolved

Inspecting and re-executing the baseline codebase revealed five silent bugs that compromised feature integrity and train/serve consistency. Each was verified and fixed in train_model.py and app.py:

  • Silent exclusion of 8 boolean risk factors: The baseline split features using select_dtypes(include=np.number) and select_dtypes(include=["object","category"]). Because pandas.bool matches neither selector and ColumnTransformer defaults to remainder="drop", eight clinical boolean fields (is_pregnant, family_history_diabetes, previous_gdm, physically_active, has_hypertension, previous_macrosomia, pcos, hiv_positive) were silently dropped from every model while still being requested in the Streamlit UI. Fixed by casting all eight to integer and listing NUMERIC_FEATURES explicitly.
  • Structural parity imputation: Replaced whole-column median imputation on parity with explicit fillna(0) for non-pregnant patients.
  • No-op Optuna hyperparameter search: The baseline called cross_validate(..., scoring="roc_auc") (which outputs test_score) but read scores["test_roc_auc"] inside a bare except Exception: return 0.0 block, causing all trials to tie at 0.0. Fixed by passing scoring={"roc_auc": "roc_auc"}.
  • UI category mismatch with OneHotEncoder: Fixed Streamlit selectboxes for education (Primary, Secondary, Higher) and bmi_category (Normal, Overweight, Obese I, Obese II+) to match the exact training schema rather than sending unknown strings that encoded to all-zeros.
  • Operator-precedence bug in engineered renal risk: Fixed creatinine * (1 if hypertension=="Yes" else 0 + 1) (which always multiplied by 1 because + binds tighter than the ternary expression) to creatinine_mg_dl * (has_hypertension + 1) across both training and inference.

5. Results, model comparison & explainability

Six candidate classifiers were evaluated under 5-fold stratified cross-validation (`StratifiedKFold(n_splits=5, shuffle=True, random_state=42)`) using an imblearn.Pipeline that applies median/mode imputation, RobustScaler, OneHotEncoder(drop="first"), and SMOTE(random_state=42) strictly inside each training fold:

XGBoost (Optuna-tuned: 0.99982)0.99640.99930.99580.99760.9998

6. Limitations, trade-offs & key takeaways

Key analytical limitations: 1. Synthetic data & non-clinical scope: Built on a synthetic educational dataset; it has no clinical validation or medical approval and must never be used for patient diagnosis. 2. Diagnostic label circularity: Because fasting glucose and HbA1c are included as predictors, the 0.9995 ROC-AUC measures rule recovery, not pre-laboratory risk prediction. Screening individuals before bloodwork is available would require retraining without glycemic labs, resulting in substantially lower separation. 3. Suppressor effects in linear coefficients: Correlated engineered interactions (such as renal_risk and glucose_hba1c_ratio) shift individual main-effect signs, requiring careful statistical interpretation.

Case Study 02  ·  Workforce Analytics, Feature Ablation & Imbalanced Classification  ·  Completed Portfolio Project

Employee Attrition Prediction — Workforce Retention Analysis & Minority-Class Recall Optimization

An end-to-end exploratory and predictive modelling study on the IBM HR Analytics Employee Attrition dataset (1,470 employees, 237 leavers), examining organizational correlates of turnover, validating engineered features through ablation testing, and deploying a recall-oriented Logistic Regression screening tool in Streamlit.

View source code (GitHub) Open live Streamlit demo (may take 30–60s to wake)
1,470Employee records analyzed
16.12%Base attrition rate (237 left)
0.82875-fold CV ROC-AUC (winner)
0.6809Held-out test recall (0.8134 AUC)

1. Project overview & problem context

In workforce retention analytics, overall classification accuracy is a misleading metric: on a dataset where 83.88% of employees stay, a trivial classifier predicting zero turnover achieves 83.9% accuracy while catching zero flight risks. Furthermore, an earlier draft notebook failed at the encoding step due to undefined variable references (target and df_encoded) and mismatched ordinal text mappings between the notebook and application.

2. Objectives & technology stack

  • Rebuild the data cleaning, feature engineering, and evaluation workflow cleanly from raw CSV to serialized pipeline artifact (attrition_production_model.pkl).
  • Quantify descriptive turnover patterns across overtime, job roles, compensation quartiles, tenure bands, and satisfaction scores.
  • Stack: Python, pandas, NumPy, scikit-learn, imbalanced-learn (SMOTE), XGBoost, Matplotlib, Seaborn, Plotly, Streamlit, AppTest.

3. Dataset constraints, schema hygiene & exploratory findings

The dataset (WA_Fn-UseC_-HR-Employee-Attrition.csv) comprises 1,470 employee records across 35 raw columns. Four non-informative fields are removed prior to analysis: three constant columns (EmployeeCount = 1, StandardHours = 80, Over18 = 'Y') and the row identifier (EmployeeNumber). That leaves 30 predictive attributes (23 numeric/ordinal and 7 categorical), plus four engineered features.

  • Overtime split (~3× baseline): Employees working overtime exhibit a 30.53% attrition rate compared to 10.44% among employees who do not work overtime.
  • Role-specific concentration: Sales Representative records the highest turnover of any role at 39.76%, followed by Laboratory Technician (23.94%), Human Resources (23.08%), Sales Executive (17.48%), and Research Scientist (16.10%), down to Manager (4.90%) and Research Director (2.50%).
  • Income quartiles & tenure trajectory: Attrition in the lowest monthly income quartile reaches 29.27% (vs. 14.21% medium, 10.63% high, and 10.33% very high). Across tenure bands, attrition is highest in years 0–2 (29.82%), declines through years 2–5 (13.82%), 5–10 (12.28%), and 10–20 (6.67%), and shows a small sample uptick in the 20+ cohort (12.12%).
  • Satisfaction gradient: Low ratings on JobInvolvement (33.73% attrition), EnvironmentSatisfaction (25.35%), JobSatisfaction (22.84%), and RelationshipSatisfaction (20.65%) consistently align with elevated turnover.

4. Methodology, ordinal alignment & feature ablation check

To prevent train/serve skew between the notebook and the Streamlit form, all seven ordinal survey columns (Education, EnvironmentSatisfaction, JobInvolvement, JobSatisfaction, RelationshipSatisfaction, PerformanceRating, WorkLifeBalance) are modeled directly on their raw integer codes (1–5), using a single shared ORDINAL_LABELS dictionary exclusively for human-readable UI display.

Rather than assuming that the four engineered features (`TenureBand`, `AgeBand`, `IncomePerSatisfaction`, and `EngagementScore`) improve generalization, an explicit ablation test was run in train_model.py on the held-out 20% test split:

  • Held-out test ROC-AUC without engineered features: 0.7965
  • Held-out test ROC-AUC with engineered features: 0.8134 (+0.0170 improvement verified on untouched test data).

5. Model evaluation & business interpretation

Four candidate models were evaluated on the 80% training split using 5-fold stratified cross-validation with StandardScaler, OneHotEncoder(drop="first"), and in-fold SMOTE(random_state=42):

While Random Forest (87.41% accuracy) and XGBoost (87.58% accuracy) achieve higher overall accuracy, they miss more than 60% of actual leavers (recall of 0.3474 and 0.3895). Logistic Regression achieves the highest cross-validated ROC-AUC (0.8287) and nearly doubles minority-class recall (0.6947 in CV; 0.6809 on the held-out test set, with test ROC-AUC 0.8134, accuracy 0.7857, precision 0.4000, and F1 0.5039).

6. Limitations, trade-offs & key takeaways

Key analytical limitations: 1. Observational associations, not causation: Model coefficients and subgroup splits on this public IBM dataset establish statistical associations, not causal mechanisms or real organizational outcomes. 2. Precision vs. recall trade-off: Prioritizing leaver recall (0.6809) yields a held-out test precision of 0.4000—roughly 6 in 10 flagged employees will not leave. High risk scores should prompt a supportive manager conversation, never an automated HR action. 3. Single-dataset scope: Trained on 1,470 records (237 positive cases); small sub-cohorts (such as 20+ year tenure veterans) have wide uncertainty bands.

Credit Risk Assessment — Data-Driven Lending Decisions & Threshold Optimization on 32,581 Loan Records

An analytical and predictive modelling project examining consumer credit default risk across 32,581 loan records, comparing a rule-based heuristic, a Decision Tree baseline, and a grid-searched Random Forest + SMOTE pipeline with an F1-optimized decision threshold persisted directly alongside the model artifact.

View source code (GitHub)

1. Project overview & problem context

In credit underwriting, a raw probability of default must ultimately translate into a transparent approval or decline recommendation governed by institutional risk appetite. Optimizing solely for headline accuracy on an imbalanced loan book (where 78.18% of borrowers do not default) results in high precision but unacceptably low default recall—missing risky loans that drive credit losses.

2. Objectives & technology stack

  • Evaluate 32,581 loan records across 11 applicant, credit-bureau, and loan attributes without leaking EDA heuristic scores into the feature matrix.
  • Improve default recall over a Decision Tree baseline using an in-pipeline SMOTE + Random Forest classifier and tune the probability cutoff (`0.62`).
  • Stack: Python, pandas, NumPy, scikit-learn, imbalanced-learn (SMOTE), Matplotlib, Seaborn, joblib, Streamlit.

3. Dataset structure, preprocessing & leakage prevention

The source dataset (data/credit_risk_dataset.csv, 32,581 rows × 12 columns) records loan_status (1 = Default for 7,108 rows / 21.82%; 0 = No Default for 25,473 rows / 78.18%) across seven numeric features (person_age, person_income, person_emp_length, loan_amnt, loan_int_rate, loan_percent_income, cb_person_cred_hist_length) and four categorical features (person_home_ownership, loan_intent, loan_grade, cb_person_default_on_file).

  • Outlier-robust imputation & pipeline encapsulation: Missing values in person_emp_length and loan_int_rate are handled via median imputation inside a ColumnTransformer paired with StandardScaler for numeric columns and mode imputation + OneHotEncoder(drop="first", handle_unknown="ignore") for categorical columns.
  • Strict exclusion of exploratory heuristic: During exploratory analysis in CREDIT_RISK_ASSESSMENT.ipynb, a domain point-scoring function (Heuristic_Risk_Category) was constructed for baseline comparison. That column is explicitly dropped before splitting into the 80% training set (26,064 rows) and 20% stratified test set (6,517 rows, 1,422 defaults) so the machine-learning models learn strictly from raw applicant and loan features.

4. Model evaluation, threshold tuning & technical implementation

In CREDIT_RISK_ASSESSMENT.ipynb, a 5-fold stratified GridSearchCV (54 parameter combinations = 270 fits, optimizing for default recall) selected a Random Forest configuration with n_estimators=100, max_depth=10, min_samples_split=10, and min_samples_leaf=4 paired with in-fold SMOTE(k_neighbors=5, random_state=42) and class_weight="balanced".

Compared to the Decision Tree baseline, Random Forest + SMOTE increases default recall from 56.75% to 74.12% (catching 1,054 of 1,422 test defaults vs. 368 missed defaults and 223 false alarms at the 0.50 cutoff) and lifts ROC-AUC from 0.8736 to 0.9202. Sweeping 50 candidate cutoffs across 0.10–0.90 identified 0.62 as the F1-maximizing threshold (F1 = 0.8011, recall = 0.6997). Both the fitted pipeline and threshold = 0.62 are serialized together in credit_risk_production_model.pkl and loaded directly by credit_risk_assessment.py.

5. Limitations, trade-offs & key takeaways

Key analytical limitations: 1. Portfolio case study, not a regulated credit-scoring system: Trained on a public Kaggle consumer loan dataset; it has not been adopted by any financial institution or validated for regulatory lending compliance (such as fair-lending disparate impact, probability calibration, or macroeconomic drift). 2. Threshold tuning on the test split: In the notebook, the 0.62 threshold sweep and initial median imputation were executed across the test/full dataset rather than an isolated validation fold; a production deployment should tune thresholds on out-of-fold validation predictions and compute loan_percent_income automatically from loan amount and income. 3. Instance-level explainability: Unlike the Diabetes SHAP workflow, the Random Forest app currently provides global feature importances and probability vs. threshold comparisons rather than per-applicant SHAP reason codes.

Mandatory Synthetic-Data & Organisational Disclosure: GrainFlow Analytics is a 100% synthetic, hypothetical portfolio case study (generated deterministically under SEED = 42). Initially conceived around Zimbabwean grain aggregation challenges and formally re-scoped in Phase 0 (DEC-001) to six South African provinces denominated in South African Rand (ZAR), it is not an implementation for the Grain Marketing Board (GMB), any real South African or Zimbabwean agricultural cooperative, or any commercial/government entity. All scenario outputs (including the +15% fuel shock and Option M3 rail modal shift) represent simulated planning calculations, never observed operational savings.

1. Project overview & problem context

Grain aggregation cooperatives face tight operational margins across rural intake depots, where seasonal harvest surges, high moisture content, physical storage/transit losses, and diesel price volatility simultaneously affect cash flow and smallholder farmer payouts. This project engineers an auditable data platform from synthetic intake weighbridge events through normalized PostgreSQL storage and Excel unit-economics schedules to executive BI reporting.

2. Six core management questions (MQ-01 to MQ-06)

  • MQ-01 Storage Capacity: Which depots are approaching silo storage-capacity limits?
  • MQ-02 District Rejections: Which districts have the highest grain rejection rates?
  • MQ-03 Quality & Grading: How do moisture and quality defects affect grading and farmer payouts?
  • MQ-04 Transport Efficiency: Which transport methods are most cost-effective per MT-km?
  • MQ-05 Physical Shrinkage: How much grain is lost during storage and outbound transit?
  • MQ-06 Fuel Sensitivity: What is the financial impact of a +15% fuel cost shock and mitigation levers?

3. Dataset scope, governance & multi-layer technical implementation

The platform covers a 12-month historical operational window (2025-01-01 to 2025-12-31, with a 15-day settlement and receipt tail through 2026-01-15) across 400 synthetic smallholder farmers, 18 districts in 6 provinces, 8 regional collection depots, 5 grain commodities (Maize, Soybeans, Sunflower, Wheat, Sorghum), 3,000 intake deliveries, 1,531 outbound shipments, and 12 commercial buyers.

  • Phases 0–3 (Governance, Synthetic Generation & 22 Quality Gates): Authored formal business requirements, assumptions register (ASM-001–ASM-019), and decision log (DEC-001–DEC-018). Built a deterministic Python generator producing 15 raw CSV files (56,479 total rows, 167 columns, SHA-256 verified) and a 22-gate Python validation engine verifying mass conservation (submitted = accepted + rejected) and split-grade partial-rejection salvage rules (POD-01).
  • Phase 4 (PostgreSQL 16.4 3NF & Star-Schema Layer): Implemented 15 normalized 3NF operational tables using exact fixed-point NUMERIC(p,s) types to eliminate binary floating-point drift. Enforced a partial unique index (WHERE is_final_inspection = TRUE) on quality_inspections (3,285 rows across 3,000 deliveries) so joining inspections to deliveries never creates a 1:N fan trap, plus composite foreign keys on farmer_payments and buyer_receipts. Compiled 11 read-only star-schema SQL views (7 conformed dimensions, 4 facts, 49,050 rows).
  • Phase 5 & Phase 6 (7 Python EDA Notebooks & 12-Sheet Excel Financial Model): Executed 7 diagnostic Jupyter notebooks connected to PostgreSQL 16.4 and built excel/GrainFlow_Analytics_Financial_Model.xlsx (12 worksheets, zero formula errors), establishing the governed distinction between cash-basis contribution and inventory-adjusted accrual operating results (DEC-013 / GB-01–GB-05).
  • Phase 7 (Power BI Semantic Model, 78 DAX Measures & Visual Suite): Built dual-mode Power Query (M) scripts, a Tabular Object Model (powerbi/model/model.bim, compatibility level 1550) with 14 tables and 17 relationships (15 active, 2 inactive role-playing date links), 78 explicit DAX measures across 5 display folders, 6 standalone 1760×990 SVG vector blueprints, and an interactive 6-page HTML simulator.

6. Project governance, limitations & honest self-assessment

In accordance with the repository's governance records (docs/PROJECT_DECISION_LOG.md v2.0.0, DEC-001 through DEC-018), Phases 0 through 7 are formally approved and closed, and Phase 8 self-assessment documentation (docs/PROJECT_SELF_ASSESSMENT_AND_IMPROVEMENT_ROADMAP.md) is complete. Key project limitations include:

  • Configured synthetic distributions & descriptive scope: All empirical patterns (such as Lichtenburg's 93.44% peak or District 13's 11.20% rejection rate) reflect deterministic mathematical parameters configured in the synthetic generator. The analysis is descriptive and scenario-based; it does not include inferential hypothesis tests or predictive time-series forecasting.
  • Simplified linear CVP & monthly working-capital grain: Break-even calculations assume a constant linear contribution margin (R 179.98/MT) and fixed depot overhead (R 14.58M) without stepped capacity costs, and working capital is tracked at a monthly grain (-R 123.91M cumulative deficit at end of July 2025) rather than intramonth daily cash balances.
  • Local batch architecture & desktop BI assembly: Data loads via batch CSV and local PostgreSQL 16.4 scripts rather than cloud ELT orchestration, and compiling a native .pbix file remains a documented manual Power BI Desktop step.
