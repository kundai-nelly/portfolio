02

How I work

I came at this from underneath. Two years of administering MySQL and Postgres, tuning queries that had been written in a hurry, and testing restores nobody had tested. That leaves you suspicious of clean-looking data, because you have seen where it comes from.

So the first thing I do with a new dataset is look for the columns that shouldn't be there. On the diabetes project that took the frame from forty columns to twenty-three and dropped the model from a suspicious 1.000 AUC to something a clinician could argue with. It is the least glamorous part of the work and it decides everything downstream.

After that I check that a difference is real before I let it become a feature. Chi-square and t-tests are cheap, and they stop you engineering something from noise. Then I read recall on the small class rather than the headline accuracy, because 84% accuracy on a dataset where 84% of people stay is not a model, it is a shrug.

Everything ends up behind an interface. Four of these six are Streamlit apps because a model that only runs in my notebook is not finished, and because the argument you have with a stakeholder is much shorter when they can move the sliders themselves.

01  ·  Diabetes_Risk_Analysis.ipynb  ·  screening model

Diabetes risk on 10,000 African patient records

The original pipeline was already fairly sophisticated — this wasn't a case of sloppy code. But re-running its own logic surfaced five real, previously-undisclosed bugs, the worst of which silently dropped eight risk factors from every model it fit.

So the project ended up being about finding those five, fixing them, and being honest about one thing fixing them can't change: the label itself is built from two of the input features.

10,000patients
74.6%diabetic (majority class)
8risk factors that were inert
0.9995CV ROC-AUC, shipped model

The bug that mattered most

X.select_dtypes(include=np.number) and X.select_dtypes(include=["object","category"]) — the original's entire feature-selection logic — silently missed every boolean column, because pandas.bool is neither. With ColumnTransformer's default remainder="drop", that excluded family history, hypertension, PCOS, HIV status, physical activity, previous GDM, previous macrosomia, and current pregnancy status from all six models compared. The Streamlit form asked a clinician to enter all eight — every one of those inputs was cosmetic; the model never learned from them. Confirmed by reproducing the original's exact selection code and diffing the columns it picked against the real column list. Fixed by casting them to int and including them explicitly — family_history_diabetes and renal_risk (creatinine × hypertension) now carry real, non-trivial coefficients in the shipped model.

Four more, smaller

Parity imputed from the wrong population. It's recorded only for the 1.4% of rows where the patient is currently pregnant — everyone else, including all 4,900 men, is NaN because the field doesn't apply, not because it's missing. Median-imputing across the whole column fabricated "2 prior pregnancies" for every man in the dataset. Fixed: impute 0 for anyone not currently pregnant.

Optuna's tuning was a no-op. cross_validate(..., scoring="roc_auc") returns its score under the key "test_score", not "test_roc_auc". Every one of 30 trials raised KeyError, was caught by a blanket except Exception, and returned 0.0 — all 30 trials tied at zero, so the search had no signal. Fixed by passing scoring as a dict, which keeps the metric name in the result key.

The app's dropdowns offered categories that don't exist in the data. Education offered None/Tertiary; the real categories are Primary/Secondary/Higher. BMI category offered Underweight/Obese; the real categories are Normal/Overweight/Obese I/Obese II+. OneHotEncoder(handle_unknown="ignore") doesn't error on a mismatch — it silently encodes it as all-zeros, so either option fed the model no signal at all. Fixed to match the real categories.

A one-character precedence bug in the app. renal = creatinine * (1 if hypertension=="Yes" else 0 + 1) — Python's ternary binds looser than +, so both branches evaluate to 1. Every hypertensive patient scored through the app got a feature value inconsistent with what the model was actually trained on. Fixed in both places.

The elephant in the room

A one-line rule — fasting_glucose_mg_dl >= 126 or hba1c_percent >= 6.5, the actual WHO/ADA diagnostic thresholds — matches this dataset's label 99.24% of the time. That's not this data being unusually predictable; the label was built from the same two values the model also gets as input.

Shipped anyway: Logistic Regression, despite ranking last by a margin (0.0005 ROC-AUC) that's genuinely meaningless at this scale. SHAP explainability is the app's whole second act, and a LinearExplainer on this model computes exact SHAP values analytically — near-instant, versus ~7 seconds per row for a generic explainer on a boosted tree.

Run it

22 real inputs plus 4 engineered features computed live in the greyed-out fields (glucose ÷ HbA1c, cholesterol ÷ HDL, BMI × age, and the fixed renal-risk term). Every one of them now actually reaches the model — change anything and it rescores with the real fitted coefficients.

Who leaves, and a pipeline that had to be rebuilt to find out

1,470 employees, 237 of them gone. The EDA in the uploaded notebook was real and ran fine — but everything after it, the entire encode-to-model section, never actually executed. Two variables were referenced without ever being defined, and every cell downstream failed the same way: a cascade of NameErrors to the last line. No model, confusion matrix, or saved artifact ever came out of it.

What was actually broken

features_to_drop = [target, 'Attrition_Flag'] — target and df_encoded are never defined anywhere earlier in the notebook. That first line threw NameError, and every cell after it — train/test split, two Decision Tree fits, a confusion matrix, feature importance, SMOTE resampling, and a final SMOTE+Random Forest section — failed the same way. One cell even raised NotFittedError on a model that existed by name but had never been .fit(). This wasn't a bug to patch; the whole pipeline had to be built from nothing.

Two smaller, real issues found along the way: the notebook and the Streamlit app each invented their own, mutually inconsistent text labels for the same 1–5 survey codes — had either been used to build the model's dummy columns, the app's inputs and the trained model's columns would have silently misaligned. Fixed by modeling on the raw integer codes everywhere and keeping exactly one label dictionary, used only for display. And a Job Satisfaction chart in the original silently overwrote that column back to numeric mid-notebook, breaking symmetry with the other three satisfaction fields for everything downstream of it.

The model, and what it gets wrong

The original's encoding loop was guarded by if df[col].dtype == 'object': — which is False for every string column on current pandas (3.0+ defaults string columns to a new dtype, not object). The label-encoding step never ran, and the model was silently fit on raw string columns, no error anywhere. Re-running it honestly also disproved its own write-up: the closing markdown claimed "all coefficients are negative... labels were likely reversed," but the real output has 8 of 19 coefficients positive. Nothing was reversed; the text just didn't match the code above it.

ModelAccPrecRecallF1AUC
Logistic Regression0.8030.6480.5670.6050.836
Logistic Regression (balanced)0.7260.4910.7990.6080.835
Random Forest (balanced)0.7850.6260.4790.5420.822

class_weight='balanced' does very different things to a linear model versus a forest: on logistic regression it buys a real recall jump (0.57 → 0.80) for a survivable precision cost; on the random forest it only reweights how trees split, and here it produced the lowest recall of the three. ROC-AUC — threshold-independent — is close across all three, so this is a genuine precision/recall trade-off, not a difference in how separable the classes are.

The play. A right-size-your-plan campaign aimed at high-charge month-to-month customers: either a downgrade matching what they actually use, or a discount onto an annual term. Bundle tech support and online security while you're there — both act as anchors and most of the base doesn't have them. Recall is 0.80 now, not the coin-flip it would have been on the original's broken encoding, so acting on individual scores is defensible; the remaining 75-in-374 miss rate is the honest residual.

04  ·  credit_risk_assessment.py  ·  lending

A credit decision, not a probability

The person using this needs to approve or decline. So the artifact on disk holds two things: the fitted pipeline, and the decision threshold that was tuned for it. Both come out of the same joblib load, which means the cost of a missed default is encoded in the model file rather than assumed to be 0.5 somewhere in the app code.

11inputs: 6 applicant, 5 loan
1artifact on disk
tunedthreshold, not 0.5

Why it's built this way

The app hands the pipeline a raw, unprocessed DataFrame. Encoding and scaling happen inside it, using the statistics fitted at training time, which removes the most common way these things break in production: preprocessing at serve time drifting away from preprocessing at train time.

Storing the threshold beside the pipeline has the same motive. Risk appetite changes with the business cycle and shouldn't require a redeploy. The interface returns the decision and the probability behind it, so a human can override with context the model never saw, which in lending is most of the context.

The right question, and two bugs in the way of answering it

4,600 Seattle-area sales, May–July 2014. Two source notebooks existed. One turned price prediction into a binary above/below-median classifier — a different, less useful question that says nothing about a specific listing, so it isn't used here. The other used the right framing but had two real, unrelated bugs.

4,600 → 3,692rows after trimming
$107,849test RMSE
0.737test R²
Ridgebeats every tree model here

Two bugs, confirmed by re-running the code

The model comparison never ran. pipe = Pipeline(...) sat inside the model-comparison loop, but every evaluation line after it — cross_val_score, .fit(), the metrics, results.append() — was indented one level outside it. Python doesn't error on that; it just built five Pipeline objects and discarded four, then evaluated whichever was last. That's exactly why the original's comparison table has one row.

Outlier removal deleted every waterfront property. The original looped an IQR filter over every numeric column, including waterfront (a 0/1 flag, ~99% zero) and view (an ordinal 0–4 score, heavily skewed to 0). For a column that's almost all one value, IQR bounds collapse to that value — so the filter dropped every row that wasn't. 33 waterfront homes in the raw data; zero survived the original's filter. It also compounded across columns, removing 28% of rows (4,600 → 3,316) instead of the 20% a correctly-scoped pass removes.

Fixed: IQR filtering restricted to columns where "outlier" is a meaningful idea — price and the continuous size/age fields — in a single pass: 4,600 → 3,692 rows (19.7% removed), 8 of 33 waterfront homes retained (the rest were genuine outliers on other grounds). A constant year feature (every row is 2014) was also dropped — it was contributing zero information either way.

Size, then location

sqft_living correlates strongest with price (0.57), then sqft_above (0.46) and bathrooms (0.40). view (0.21) only shows up as a real signal because the outlier-scope fix kept it — under the original filter it had already been deleted. Mutual information agrees on the ranking: size and bathroom count dominate.

Shipped: Ridge Regression — not a consolation prize for fixing the loop bug above, it genuinely beats every tree model here, XGBoost included. Plausible rather than surprising: statezip alone one-hot-encodes into dozens of sparse columns, and with 3,692 rows after cleaning, a regularized linear model generalizes better than a model with enough capacity to overfit those splits.

A one-hot dummy backed by n=1 fits noise from that single row, not a real location effect, so it's excluded from the coefficient chart below.

06  ·  completed_calander.ipynb, calendar.py  ·  tooling

The same calendar, built twice on purpose

First as a terminal application, to get the data model, the JSON persistence and the input validation right without a UI to hide behind. Then as a Streamlit app once the logic held. It's the smallest thing here and the reason it's included is the order.

2interfaces, one core
4event categories
JSONflat-file store

What it does

Events are written to disk on every change and reloaded on start, with malformed dates skipped rather than allowed to take down the read path. The Streamlit version draws the month as a Plotly heatmap with the day numbers laid over it, so a month with events reads at a glance. Add, delete and search are form-based with validation on both the date format and a non-empty description. There's a bar chart of events per month, a total, and a CSV export. The terminal version surfaces the next seven days on every refresh.

The month view, rebuilt here

The Streamlit version draws this as a Plotly heatmap. Same idea in plain markup: click a day to cycle it through the four categories, and the counts and the next-seven-days list update the way they do in the app. Nothing persists, since there is no JSON file behind a web page.

Month

What I'd fix

The date string is the primary key, which caps you at one event per day and is the sort of decision that is cheap now and expensive later; it should be an ID. JSON is fine for one user and wrong the moment there are two, so SQLite is the next step. And the clear-all confirmation doesn't survive Streamlit's rerun, so it needs session state to work as intended.
